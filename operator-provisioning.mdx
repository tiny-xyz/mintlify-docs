Operator scope is venue infrastructure. This page covers what the venue and a
contracted runner do off the wire: key custody, which hosts resolve operator
tokens, and how a new trading account comes to exist. The wire itself is the
ordinary v9 surface — cross-account REST plus the events-side subscription
vocabulary — see
[REST trading and the heartbeat deadman](/rest-trading),
[the account events WebSocket](/account-events), and
[the multi-strategy runner model](/multi-strategy).

## Two key stores, one scope rule

The gateway loads two id-disjoint `tiny-keys-v1` files at boot: `--keys` for
client tokens (also deployed to shell fronts) and `--operator-keys` for
operator tokens. Boot refuses an ID overlap, so which store resolves a
token's `key_id` decides the request's scope. Nothing inside the token
chooses.

Key files are `<key_id> <128hex>` lines with `#` comments, `0600`
permissions required, loaded once at boot. Adding, removing, or rotating a
key is a service restart, and removal is the only revocation — tokens verify
locally with no callback.

## Minting

<Steps>
  <Step title="Generate a key">
    `tiny-gateway-keytool gen <key_id>` emits one key-file line from OS
    entropy. Append it to the operator store on the boxes that hold it and
    restart them.
  </Step>
  <Step title="Mint the token">
    `tiny-gateway-keytool mint --keys <operator-store> --key-id <n>
    --account <n> --expires-at <wall-ns>` emits the canonical v9 `auth`
    frame and its hex header form. The minted account is the operator's own
    auth identity: it pays the operator's request-rate charge and needs no
    funding — trading authority comes from each request's body account.
  </Step>
  <Step title="Deliver out of band">
    Hand the runner the token, or the key line if the runner mints its own
    rotations. `expires_at` bounds the token's life; at expiry REST answers
    `401` and the events socket closes `1008`, and the runner continues with
    a fresh token — short-lived tokens rotate with no venue action.
  </Step>
</Steps>

## Which hosts resolve operator tokens

The operator store is deployed to exactly two places, and each unlocks a
different capability:

- **The gateway core's own listen address** — operator REST: cross-account
  orders, cancels, modifies, heartbeat batches, and `GET
  /v1/orders/{account}` snapshots. Shell fronts never hold the operator
  store, so an operator token presented to a shell fails `auth_failed`
  `unknown_key`. Dial the core directly on the private network;
  `ops/deploy/colo.toml` in the exchange repository is the address
  authority.
- **The account-edge tier** (when started with `--operator-keys`) — operator
  events sessions: `listen`/`unlisten` multiplexing on the events WebSocket.
- The history service accepts the same tokens for cross-account
  `GET /v1/history/account-events?account=` replay.

Trading authority and event subscriptions are independent planes: an
operator trades accounts it does not listen to (and hears nothing about
them), and listens to accounts it never trades.

## Adding a new trading account

Accounts exist by ledger funding, and funding is a boot snapshot: the gateway
boots balances from the `--funding` file (`tiny-funding-v2`, one
`<account> <micro-dollars>` line each) played through the mock chain. There
is no runtime deposit path, and a changed funding file requires an explicit
migration, never an ordinary restart.

- **Venue:** add the funding line, run the migration, confirm the account ID
  to the runner. No new keys — operator scope already reaches every
  ledger-known account.
- **Runner:** trade the account's canonical address (the `u64` ID big-endian
  in the last 8 bytes, zeros elsewhere) over REST, `listen` it on the events
  socket, include it in the heartbeat batch if it should be swept on runner
  death, and reconcile its baseline from `GET /v1/orders/{account}`.

A per-account client token — for a direct client integration beside the
operator's — is a separate mint against the client store and is never
required for operator trading.

## Deployed capacities

Defaults; the service flags and `ops/deploy/colo.toml` are the per-deploy
authority.

| Capacity | Default | Where |
| --- | ---: | --- |
| Accounts per `heartbeat`/`listen`/`unlisten` frame | 10 | frame grammar |
| Requests per second per account (gateway REST) | 30 | gateway `--account-msgs-per-sec` |
| Operator events sessions per account-edge box | 4 | account-edge `--operator-sessions` |
| Egress frames per operator events session | 32,768 | account-edge `--operator-egress-slots` |
| Listened-account subscription rows per box | 4,096 | account-edge `--subscription-slots` |
| Sessions watching one account on one box | 8 | fixed subscriber row |

Events-egress overflow closes `1013`: back off, reconnect, re-listen, and
reconcile via snapshot-then-splice. Account-edge boxes are cloned — capacity
scales by adding boxes, and no venue state lives on them.
