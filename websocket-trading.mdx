`GET /v1/ws` upgrades a fresh gateway connection into the authenticated private
stream. After authentication, the same canonical trading commands accepted by
REST can be sent as WebSocket text frames, while acknowledgements and account
events arrive on the same socket.

<Warning>
Open the upgrade on a fresh TCP connection. A keep-alive connection that has
already served an authenticated REST request refuses the upgrade.
</Warning>

## Connection sequence

<Steps>
  <Step title="Upgrade">
    Send an RFC 6455 upgrade request to `/v1/ws`. Query strings and alternate
    paths are not accepted.
  </Step>
  <Step title="Authenticate first">
    The first text message must be the canonical v7 `auth` frame. Send the JSON
    frame itself, not the hex-encoded `Tiny-v1` REST header value.
  </Step>
  <Step title="Wait for auth_ok">
    `auth_ok` confirms the session account. `auth_failed` means the credentials
    were refused. Re-authentication on an open socket is not supported.
  </Step>
  <Step title="Consume the complete baseline">
    Read from `snapshot_begin` through `snapshot_end` and verify its counts
    before treating subsequent events as the current account state.
  </Step>
  <Step title="Apply live traffic">
    Send commands as canonical text frames and apply server events using the
    ordering and idempotency rules below.
  </Step>
</Steps>

## Authentication frame

```json
{"version":7,"type":"auth","body":{"account":"42","expires_at":"1730000000000000000","key_id":1,"cancel_on_disconnect_ms":0,"sig":"<128-lowercase-hex>"}}
```

The wire requires fixed key order, no whitespace, canonical quoted decimals,
and lowercase hex. Client frames are capped at 552 bytes. See
[Authentication and canonical wire](/authentication-and-wire)
for token signing and cancel-on-disconnect behavior.

## Client-to-server messages

The private codec accepts exactly seven client message types.

| Type | Session | Purpose |
| --- | --- | --- |
| `auth` | Every session, first message only | Establish the session identity and policy |
| `new_order` | Client or operator | Submit and collateralize an order |
| `cancel_order` | Client or operator | Cancel one exchange order ID |
| `cancel_all` | Client or operator | Cancel the account's current open orders |
| `modify_order` | Client or operator | Modify an order's price using a monotone `modify_seq` |
| `listen` | Operator only | Subscribe to one account and request its baseline |
| `unlisten` | Operator only | Stop one account subscription |

Sending `listen` or `unlisten` from a normal client session produces
`bad_request` with reason `not_operator`. Sending them to a REST command route
produces `bad_type`.

### Command acknowledgements

- A WebSocket `new_order` returns `order_submitted` directly to the submitting
  session after validation, collateral lock, and durable publication.
- Cancel and modify outcomes remain asynchronous: observe `cancel_done`,
  `modify_done`, or `order_rejected`.
- `order_submitted` is not a booking or execution promise. The engine verdict is
  `order_accepted`, `order_rejected`, and any following fills.
- Rate-limited commands produce `bad_request` with reason `rate_limited`; the
  socket remains open.

## Automatic snapshot

A normal client receives this baseline immediately after `auth_ok`:

```text
snapshot_begin
market_state × live markets
snapshot_order × open orders
snapshot_position × nonempty market positions
snapshot_balance × 1
snapshot_end
```

`snapshot_end` reports counts; verify them. The snapshot is complete account
state, not a replay cursor. Its `snapshot_balance.balance_seq` is the baseline
for later absolute `balance` frames.

An operator connection receives only the venue-board baseline at authentication:
market cards bracketed by `snapshot_begin` and a venue-scope `snapshot_end`
whose account is all zeroes. Each admitted `listen` then produces a separate
account baseline. The account's `snapshot_end` confirms that subscription is
live.

## Server-to-client messages

The trading server schema contains 22 server message types. Twenty-one can
participate in the private WebSocket flow; `venue_status` is the body of the
separate `GET /v1/status` route.

### Session and command messages

| Type | Meaning |
| --- | --- |
| `auth_ok` | Authentication succeeded; echoes the numeric session account |
| `auth_failed` | Authentication failed with `bad_token`, `expired_token`, `unknown_key`, or `sanctioned` |
| `bad_request` | A sent frame or command transport rule was refused |
| `order_submitted` | New order validated, locked, and durably published; carries the exchange `order_id` |

### Order lifecycle messages

| Type | Meaning |
| --- | --- |
| `order_accepted` | Engine accepted the original order; precedes that order's fills |
| `order_rejected` | New order, cancel, cancel-all, or modify command was refused; inspect its sentinel-disciplined identity |
| `fill` | One execution with absolute remaining quantity, positions, liquidity, and fee |
| `cancel_done` | Terminal release with cause `requested`, `ioc_residual`, `gtd_expired`, `self_trade`, or `session_lost` |
| `modify_done` | Price modification applied; the order remains live with authoritative remaining quantity |
| `order_expired` | Market-close sweep terminated the order |

A rejected modify does not itself terminate the underlying order. A rejected
new order is terminal for that attempt. Classify `order_rejected` by its
`salt`, `market_id`, `order_id`, and `modify_seq` fields rather than by reason
alone.

### Money, market, and finality messages

| Type | Meaning |
| --- | --- |
| `balance` | Absolute `available`, `locked`, and `pending_finality`; highest `balance_seq` wins |
| `market_state` | Absolute market lifecycle card with `tick_step`, `fee_rate_bps`, and advertised close |
| `fill_settled` | One fill reached chain finality; decomposes proceeds, price improvement, and fee refund |
| `market_settled` | Final market payout receipt for an affected account |

### Snapshot messages

| Type | Meaning |
| --- | --- |
| `snapshot_begin` | Opens a staged baseline bracket |
| `snapshot_order` | One restable open order with last applied `modify_seq` |
| `snapshot_position` | Gross YES/NO lots and the portions pledged to open orders |
| `snapshot_balance` | Absolute three-bucket balance and its sequence baseline |
| `snapshot_end` | Closes the bracket and reports counts |

### Operator subscription messages

| Type | Meaning |
| --- | --- |
| `listen_rejected` | Subscription refused because capacity is full or the account is unknown |
| `unlisten_done` | Account is no longer subscribed; also returned when it was already absent |

## Ordering and idempotency

- WebSocket delivery orders frames on one connection, but reconnects replay no
  event history.
- Use `book_seq` for sequenced facts within a market. Never order by `ts_ms`.
- Deduplicate fills by `(market_id, book_seq, fill_index)`.
- Assign `fill.remaining`, `position_yes`, and `position_no` as absolute values;
  never subtract locally.
- Apply only a `balance` whose `balance_seq` is higher than the snapshot or last
  applied balance. The sequence is not dense.
- Apply `market_state` as a monotone lifecycle per `market_id`; duplicates are
  routine.
- Join `fill_settled` to its fill by `(market_id, book_seq, fill_index)`. Finality
  can arrive out of order across fills and is not a watermark.

## Operator multiplexing

Operator tokens are resolved by the venue's separate operator key store. The
operator socket starts with no account subscriptions and can send `listen` or
`unlisten` frames containing one canonical 40-hex address.

<Warning>
Listen before trading for an account. The direct `order_submitted` acknowledgement
returns to the submitting socket, but engine verdicts and fills route by account.
An operator that trades an unlistened account will not receive those later
events on its socket.
</Warning>

Events staged while an account baseline is being built are absorbed into that
baseline so live account traffic cannot precede it. `market_state` is a venue
fact and continues independently. Subscriptions are connection state and must
be rebuilt after reconnect.

## Liveness and close behavior

| Condition | Result |
| --- | --- |
| Normal peer or server shutdown | Close `1000` |
| Token expires | Close `1008`; reconnect with a fresh token |
| Liveness probes go unanswered | Close `1001` |
| Session or egress capacity is exhausted | Close `1013`; back off, reconnect, and snapshot |
| Client payload exceeds the 552-byte trading-frame cap | Close `1002` |
| Peer stops accepting writes for the stall deadline | Socket drops, possibly without a close frame |

The server pings a quiet session after roughly five seconds and closes after
three unanswered probes. Any inbound frame resets the probe. Clients should
drain continuously, respond to pings, and treat every close as a snapshot-based
recovery event.

## Reconnect rule

There is no replay cursor. Reconnect, authenticate, consume a complete snapshot,
then resume live application. Preserve the exact bytes of any still-retryable
`new_order`; use same-key retries for ambiguous commands rather than inventing a
replacement.
