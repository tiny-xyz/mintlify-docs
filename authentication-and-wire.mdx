Authenticated REST requests send a `Tiny-v1` authorization value on every
request. The account-events WebSocket sends the decoded auth frame as its
first text message after the upgrade.

## Authorization header

The header has this shape:

```text
Authorization: Tiny-v1 <hex-encoded-canonical-auth-frame>
```

The decoded bytes are exactly:

```json
{"version":9,"type":"auth","body":{"account":"42","expires_at":"1730000000000000000","key_id":1,"sig":"<128-lowercase-hex>"}}
```

The signature is HMAC-SHA512 over:

```text
tiny-auth-v1:<account>:<expires_at>:<key_id>
```

Use the secret selected by `key_id`. The key store that resolves the ID fixes
the request's scope: client tokens are bound to one account, while venue
operator tokens act for any ledger-known account per request. Nothing inside
the token chooses.

<Note>
The auth body carries no order-protection policy. Disconnects arm nothing and
fire nothing — order protection is the per-account heartbeat deadman on
`POST /v1/heartbeat`, described in
[REST trading and the heartbeat deadman](/rest-trading#the-heartbeat-deadman).
</Note>

## REST authority

For ordinary client requests, the address in the command body must embed the
same account as the token. A mismatch rejects as `wrong_account`.

For operator requests, the body account is the effective account, judged per
request: admission, funds, and sanctions all judge the body account, and a
body account the ledger does not know rejects `unknown_account`. Cross-account
authority is per-request REST scope — there is no session to anchor it to.

The 65-byte `sig` inside new and modified orders is a future settlement
signature slot. It is carried and journaled but not verified by the current
gateway. Send exactly 130 lowercase hex characters; zeroes are legal during
this phase.

## WebSocket authentication (account events)

The events WebSocket lives on the account-edge tier, not the trading hosts.

<Steps>
  <Step title="Open a fresh connection">
    Upgrade `GET /v1/ws` on the account-edge host, on a TCP connection that
    has not served an authenticated REST request.
  </Step>
  <Step title="Send auth first">
    The first text frame must be the canonical auth JSON, not the hex-encoded
    header form.
  </Step>
  <Step title="Expect no baseline">
    `auth_ok` confirms the session account and live events follow. The
    delivery tier holds no state: snapshot over REST, then splice the stream
    above the snapshot's `event_seq` anchor — see
    [the account events WebSocket](/account-events).
  </Step>
</Steps>

Re-authentication is refused. Reconnect to rotate credentials. Token expiry
closes with code `1008`; event backpressure closes with `1013`.

## Canonical JSON checklist

- Encode the documented key order exactly.
- Emit no spaces, newlines, or insignificant formatting.
- Use lowercase hex with no prefixes.
- Encode `u64` values as quoted canonical decimals where the schema requires
  strings: no sign and no leading zeroes.
- Emit JSON booleans as bare `true` or `false`.
- Never emit floating-point values.
- Keep each frame at or below 587 bytes.
- Do not add fields for forward compatibility; unknown fields reject.

<Warning>
Do not parse a frame into a generic map and serialize it again for retry. Map
ordering or numeric normalization can change the bytes and turn the request
into a fresh order. Retain and replay the original byte buffer.
</Warning>

## Operator subscriptions

Operator event multiplexing (`listen`/`unlisten`) is account-edge WebSocket
vocabulary, unrelated to trading authority: subscribe each account whose
events you want, and trade any ledger-known account over REST regardless. The
full contract — batching, per-account verdicts, and the empty confirmation
bracket — lives in
[the account events WebSocket](/account-events#operator-multiplexing) and
[the multi-strategy runner model](/multi-strategy); key minting lives in
[Operator provisioning](/operator-provisioning).
