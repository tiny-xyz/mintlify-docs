`GET /v1/ws` on the **account-edge host** upgrades into the authenticated account-events stream. Account-edge is a delivery tier, cloned to scale: it verifies the same tokens the gateway does, holds no venue state, and serves exactly one thing — each account's live event frames, in order, each stamped with the account's dense `event_seq`.

<Warning>
  The trading hosts serve no WebSocket — `GET /v1/ws` on a gateway or shell front answers `404`. Point event consumers at the account-edge address from your deploy configuration.
</Warning>

## Connection sequence

<Steps>
  <Step title="Upgrade">
    Send an RFC 6455 upgrade to `/v1/ws` on the account-edge host. Query strings and alternate paths are not accepted.
  </Step>
  <Step title="Authenticate first">
    The first text message must be the canonical v9 `auth` frame — the JSON itself, not the hex-encoded `Tiny-v1` header value.
  </Step>
  <Step title="Wait for auth_ok">
    `auth_ok` echoes the numeric token account. No baseline follows: the delivery tier restates no state.
  </Step>
  <Step title="Snapshot over REST, then splice">
    Buffer the stream, fetch `GET /v1/orders` on the trading surface, and apply buffered frames strictly above the snapshot's `event_seq` anchor.
  </Step>
</Steps>

A client-scope session is subscribed to its own account at open — no verb needed. Events flow from then on, one canonical frame per text frame.

### Auth refusals

- A first data frame that is not the `auth` frame answers `bad_request` `unauthenticated` and the connection ends. A control frame before auth ends the connection — a conforming client authenticates before anything else.
- A token that decodes but fails verification answers `auth_failed` with `bad_token`, `expired_token`, or `unknown_key`, then the connection ends. `sanctioned` is a retained word, not emitted at auth — a sanctioned account passes auth and is refused at trading admission, on the REST surface.
- The auth-first window rides the whole-request deadline: a peer that upgrades and then withholds its auth frame holds a connection, never a session slot — and not forever.
- Re-auth on an open session answers `bad_request` `bad_type` — the session is its token's; reconnect to rotate.

## What a session may send

The complete client vocabulary on this socket is three frames. Everything else is refused:

| Frame | Scope | Answer |
| --- | --- | --- |
| `auth` (first text frame) | Both | `auth_ok`, or `auth_failed` and the connection ends |
| `listen` | Operator | Per account: the empty confirmation bracket, or `listen_rejected` |
| `unlisten` | Operator | Per account: `unlisten_done` |

| Refused input | Answer |
| --- | --- |
| `listen` / `unlisten` on a client-scope session | `bad_request` `not_operator`; the socket stays open |
| A second `auth` | `bad_request` `bad_type`; the socket stays open |
| A frame that fails the canonical grammar | `bad_request` with the grammar reason; the socket stays open |
| A frame over the per-account rate limit | `bad_request` `rate_limited`; the socket stays open |
| Trading vocabulary (`new_order`, `cancel_order`, `cancel_all`, `modify_order`, `heartbeat`) | Session doomed; close `1013` |
| A payload over the 587-byte frame cap, unmasked data, or broken framing | Close `1002` |

A client-scope session has nothing to send after `auth`. Silence is the conforming behavior; the server's pings need only the standard automatic pongs.

## The event\_seq contract

Every delivered frame carries `event_seq` in its envelope: dense per account, starting at `"1"`, stamped by the gateway before delivery.

- **A gap means missed delivery.** Delivery is best-effort by contract — the tier may drop a frame or doom a slow session rather than buffer without bound. The dense sequence makes every hole client-visible.
- **Recovery is snapshot-then-splice**: `GET /v1/orders` answers the `event_seq` anchor its rows already reflect; resume strictly above it.
- **Deep replay** is the history plane: `GET /v1/history/account-events` serves the stored frames after any cursor, verbatim — the same envelope this stream delivers.
- The sequence is process-local to the gateway: a venue restart re-bases it. A regression means re-snapshot.

## What arrives

Two families of server frames exist on this socket. Session and subscription answers carry no `event_seq`:

| Type | Meaning |
| --- | --- |
| `auth_ok` | The accepted auth's answer; `account` is the token's numeric account id as a quoted decimal — the one frame that speaks the id rather than the 40-hex address. No baseline follows |
| `auth_failed` | Authentication refused (`bad_token` / `expired_token` / `unknown_key`); the connection ends after it |
| `bad_request` | A frame this session sent was refused; the socket stays open |
| `snapshot_begin` / `snapshot_end` | Only as a `listen`'s empty confirmation bracket — `snapshot_end` names the account with every count `0` and `event_seq` `"0"` |
| `listen_rejected` | One named account refused: `unknown_account` or `subscription_capacity`; the account echoes verbatim |
| `unlisten_done` | The unlisten applied for one named account, also when it was never listened |

Everything else is an account event under its dense `event_seq` stamp, each body opening with the `account` it belongs to.

## Event vocabulary

| Type | Meaning |
| --- | --- |
| `order_accepted` | Engine accepted the order; precedes that order's fills |
| `order_rejected` | An asynchronous refusal; inspect its sentinel-disciplined identity |
| `fill` | One execution with absolute remaining quantity, positions, liquidity, and fee |
| `cancel_done` | Terminal release with cause `requested`, `ioc_residual`, `gtd_expired`, `self_trade`, or `session_lost` |
| `modify_done` | Price modification applied; the order remains live |
| `order_expired` | Market-close sweep terminated the order |
| `balance` | Absolute three-bucket balance; highest `balance_seq` wins |
| `market_state` | Lifecycle card for a market the account holds a position in |
| `fill_settled` | One fill reached chain finality; decomposes the promoted amount |
| `market_settled` | Final market payout receipt |

Application rules (dedup keys, absolute values, ordering) are in [Events and recovery](/events-and-recovery).

## Operator multiplexing

Operator-scope sessions hear nothing at connect and subscribe explicitly:

```json
{"version":9,"type":"listen","body":{"accounts":["000000000000000000000000000000000000002a","0000000000000000000000000000000000000063"]}}
```

- `listen` and `unlisten` each name 1–10 distinct canonical addresses, judged independently in frame order — one refused account never voids the others. An empty, over-cap, or duplicate-carrying list refuses the frame shape as `bad_request` `bad_account_batch`.
- An admitted listen answers an **empty confirmation bracket**: `snapshot_begin`, then `snapshot_end` naming the account with every count `0` and `event_seq` `"0"`. The delivery tier restates no state and knows no anchor — reconcile each account against the gateway's snapshot, exactly as a client session would.
- A refused account answers its own `listen_rejected`: `unknown_account` (the address is not the canonical embedded form, so no event could ever route to it) or `subscription_capacity` (the account's subscriber row is full — a fixed number of sessions may watch one account at a time).
- `unlisten` answers `unlisten_done`, also for a never-listened account — the goal state holds. Frames already queued behind the acknowledgement may still drain. Unlistening never touches the heartbeat deadman: an armed account stays armed until its window lapses or a disarming heartbeat lands.
- Subscriptions are session state: a reconnect starts from zero and re-listens.
- `listen` on a client-scope session answers `bad_request` `not_operator`.

## What this socket refuses

Trading vocabulary has no meaning here. A session that sends `new_order`, `cancel_order`, `cancel_all`, `modify_order`, or `heartbeat` frames is a misdirected client and is **doomed** — the connection closes `1013` rather than half-serving a session pointed at the wrong endpoint. Commands are REST, on the trading surface; order protection is `POST /v1/heartbeat`, not this socket's liveness. Grammar, scope, and rate refusals are gentler: they answer `bad_request` in-band and keep the socket, as tabled above.

## Connect refusals

| Refusal | Meaning |
| --- | --- |
| HTTP `400` | A bad upgrade shape, or the socket already served an authenticated REST request — one socket, one transport session; upgrade on a fresh connection |
| HTTP `404` | This host serves no WebSocket — you dialed a trading front; use the account-edge address |
| Close `1013` right after auth | No session slot is free, or (client scope) the account's subscriber row is full — a session that would never receive events is refused rather than silently served. Back off and retry |

## Liveness and close behavior

| Condition | Result |
| --- | --- |
| Normal peer or server shutdown | Close `1000` |
| Token expires | Close `1008`; reconnect with a fresh token — no private frame is ever sent past the token boundary |
| Liveness probes go unanswered | Close `1001` |
| Egress backpressure (slow consumer) or ingress saturation | Close `1013`; back off, reconnect, snapshot, splice |
| Client payload exceeds the 587-byte frame cap, unmasked data, or broken framing | Close `1002` |
| Trading vocabulary sent here | Close `1013` (doomed) |

The server pings a quiet session and closes `1001` after unanswered probes; any inbound frame resets the probe, and the standard automatic pong answers it. Drain continuously and treat every close as a snapshot-then-splice recovery event.
